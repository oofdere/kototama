# Rust ↔ Swift: porting kototama

This is the write-up the Swift port was made for: what it was like to port
`rusty-llama` to Swift, how the two languages feel to work in against the same
llama.cpp, and how fast each side actually runs. Everything here is backed by
the two codebases in this repository — the Rust crate at the root, the Swift
package in [`swift/`](README.md) — which run the same pinned llama.cpp commit
with the same build flags.

**Verdict up front:** the Swift port is genuinely nicer to read and to write
for this particular job — a safe, synchronous, single-machine wrapper over a
C library — and it runs at parity with Rust (within a few percent on every
benchmark that matters, differences well inside noise). Rust's real edge here
is not speed but the compile-time guarantees, and the port makes visible which
of those the Rust crate was actually leaning on. Two of Rust's biggest pieces
of machinery — the actor and the `unsafe impl Send/Sync` proofs — exist to work
around the absence of what Swift gives you natively, and the Swift code gets
smaller when they come out.

## What was ported

The full surface, one to one:

| Area | Rust | Swift |
|---|---|---|
| Core | `Model`, vocab queries, `Context`, `Sequence`, `Batch`, `Backend` | `Model`, `Vocabulary`, `Context`, `TokenSequence`, `TokenBatch`, `Backend` |
| Samplers | `Greedy`, `Temperature`, `TopK`, `TopP`, `MinP`, `Typical`, `TopNSigma`, `Xtc`, `Dist`, `Chain` | the same ten, same semantics |
| Examples | `simple.rs`, `simple_chat.rs` | `simple`, `SimpleChat`, same flags and output |
| Benchmarks | `benches/inference.rs` (criterion, 6 benches) | `kototama-bench` (6 matching benches) |
| Tests | 123 tests incl. 6 insta snapshots + 1 doctest | 120 tests incl. 6 snapshot tests |

The evidence that the port is faithful is not "it compiles" but the snapshot
tests. The Rust crate snapshots token streams from tokenize and greedy
generation; those expected values were ported **verbatim** into
`swift/Tests/KototamaTests/Snapshots/*.json`, and the Swift suite passes them
unchanged. The two examples were also run side by side on the same prompt and
produced byte-identical text:

```
<|start_story|> Once upon a time, a little girl named Lily lived in a small
house with her mom. Lily loved to play with her toys and make them look nice.
One day, Lily saw a small bird on the ground. She
```

117 of the test names map one-to-one across the suites. Five Rust tests have no
Swift meaning and were deliberately not ported — two exercise `Backend`'s
reference counting (which the port replaces with a lazy singleton), one
verifies `Arc` drop semantics, one pins the Rust `&self`/`&mut self` borrow
contract, and one is an `init` smoke test. Three Swift tests replace them with
assertions that are meaningful in Swift (singleton identity, a fresh sequence
having no logits, loading through the shared backend).

## The same problem, two languages

The most interesting thing in the Rust crate is how it makes a
`llama_context` safe. A llama.cpp context is not thread-safe; it must be used
from one thread at a time. The Rust crate answers this with an actor: every
operation is a message to a dedicated thread, generated by the `#[protocol]`
macro.

```rust
// Rust: the actor protocol (src/context.rs)
#[protocol]
pub(crate) trait ContextProtocol: Send + Sync {
    fn checkout_seq(&self) -> Response<Option<llama_seq_id>>;
    fn push_token(&self, token: llama_token, pos: llama_pos, seq_id: llama_seq_id)
        -> Response<Result<Vec<f32>, DecodeError>>;
    fn sample_token(&self, sampler: SamplerPtr) -> Response<llama_token>;
    // ... ten more messages
}
```

That is roughly 130 lines of protocol trait, message handlers, and an
`ActorRef` wrapper — plus a `SamplerPtr` raw-pointer wrapper with its own
`unsafe impl Send` and a safety comment explaining why dereferencing it is
sound. It works, it is thread-safe, and every call to `seq.push(token)` is a
round trip through a channel to another thread.

Swift has actors in the language, so this was the obvious port. But the API
the Rust crate exposes is synchronous: `Sequence::push` blocks until the decode
returns anyway. The actor is not making the API concurrent, it is making the
*access* serial. That is a lock's job.

```swift
// Swift: one lock, same guarantee (Sources/Kototama/Context.swift)
public final class Context: @unchecked Sendable {
    /// Everything that must stay consistent under one lock.
    private let state: Mutex<ContextState>

    func pushToken(_ token: Token, at pos: Position, seq id: SequenceID) throws -> [Float] {
        try state.withLock { state in
            state.batch.clear()
            try state.batch.add(token: token, pos: pos, seqIDs: [id], wantsLogits: true)
            let status = llama_decode(state.handle, state.batch.cBatch)
            guard status == 0 else { throw KototamaError.decodeFailed(DecodeError(status: status)) }
            return Array(UnsafeBufferPointer(start: llama_get_logits_ith(state.handle, 0), count: Int(state.nVocabulary)))
        }
    }
}
```

The invariant is identical — one mutation at a time on the C pointer — and the
caller never blocks on a channel hop. The port keeps the `@unchecked Sendable`
annotation, which is the honest part: Swift will not prove this for you either,
it just makes the opt-in a three-word annotation instead of an `unsafe impl`
plus a multi-paragraph safety comment and a helper type for the sampler
pointer. Rust's version is more explicit about *why* it is sound; Swift's
version is 130 lines shorter and the reason is in one doc comment. Whether that
trade is acceptable depends on how much you trust the comment.

One place Rust wins outright: `Sequence` is not `Sync` in Rust and the compiler
enforces it. The Swift `TokenSequence` is a class, so two threads *can* touch
one generation at once; the class is marked non-`Sendable`, which Swift 6's
concurrency checker catches at the same points Rust's borrow checker would —
but only in checked code. Swift's concurrency guarantees are real and catch
transfers across actors and tasks; they are just not as total as Rust's
ownership model.

## Errors: `Result<_, ()>` versus `throws`

This is where the Swift port gets noticeably more pleasant. Most fallible
Rust operations return `Result<T, ()>`:

```rust
pub fn load_from_file(path: &str, params: ModelParams) -> Result<Self, ()> {
    let model = unsafe { llama_model_load_from_file(path.as_ptr(), params.into()) };
    if model.is_null() { return Err(()); }
    ...
}
```

`Err(())` says *that* something failed and nothing about *why*, and every call
site ends in `.expect("Failed to load model")` or `map_err(|_| ())`. The Swift
port carries real diagnoses:

```swift
public enum KototamaError: Error, Equatable, Sendable, CustomStringConvertible {
    case modelLoadFailed(path: String)
    case tokenizationFailed(text: String)
    case pieceConversionFailed(token: Token)
    case decodeFailed(DecodeError)
    // ...
}
```

This is a port-quality choice, not a language difference — Rust could define
this enum just as easily — but the language nudges: Swift's `throws` has one
spelling at the definition and the call site, and error messages that print
themselves via `CustomStringConvertible` are the path of least resistance.

## Naming and readability

The port names things for humans, and where Swift and Rust conventions differ,
it follows each language's own style guide rather than mirroring the other
side:

- Rust `ContextParams` wraps a C struct and derefs to it; Swift
  `ContextParams` names the five fields a caller actually tunes and documents
  where the rest of llama.cpp's knobs live.
- Rust's `n_gpu_layers` becomes `nGPULayers` (Swift API guidelines), while
  `noPerf` keeps the double negative because it maps to the C `no_perf` field
  and renaming it would break the correspondence.
- Rust `Sequence::tokens()` returns `&[i32]`; Swift `TokenSequence.tokens` is a
  plain array, and `Token`/`Position`/`SequenceID` are distinct structs where
  Rust uses type aliases over `i32`. The alias is zero-cost; the struct makes
  `push(token, at: position)` readable at the call site and stops a position
  being passed where a token belongs.
- Rust's `Sampler::apply_mut` / `apply` pair becomes `transformInPlace(_:)` /
  `transform(_:)`, per Swift's label-based convention for the mutating /
  returning pair.

Where the Rust code is *already* clear, the Swift is nearly a line-for-line
translation. Here is `TopP` in both, which is representative of the sampler
family:

```rust
// Rust (src/samplers/top_p.rs)
let max = logits.iter().copied().fold(f32::NEG_INFINITY, f32::max);
let exps: Vec<f32> = logits.iter().map(|&l| (l - max).exp()).collect();
let sum: f32 = exps.iter().copied().sum();
let probs: Vec<f32> = exps.iter().map(|&e| e / sum).collect();
```

```swift
// Swift (Sources/Kototama/Samplers/TopP.swift)
let probabilities = softmax(logits)   // same three steps, shared helper
```

The only structural change in the whole sampler port: three samplers each
inline the same softmax-over-a-copy code in Rust, and the Swift version puts
it in one `softmax(_:)` helper. Everything else, including subtleties like
Top-K's tie-preserving threshold and Min-P's `minKeep` floor, is the same
algorithm with the same pinned test cases.

One sampling semantic is deliberately *not* copied. Rust's
`Sequence::sample` applies a sampler twice — it calls `sampler.apply(logits)`
and then `sampler.sample(&transformed)`, and the trait's default `sample`
transforms again before argmax. That is invisible for selectors (`Greedy`,
`Dist`) whose transform is the identity, but it means a `Temperature` or
`TopK` passed to `sequence.sample(_:)` runs twice in Rust. The Swift
`TokenSequence.sample(_:)` applies it once, which is what `Sampler::sample`
is documented to do. Similarly, `Chain::sample` in both languages delegates to
its last stage after transforming, so a trailing *transform* (as opposed to a
selector) is applied twice in both — kept as-is for parity, and harmless for
the usual `transform -> transform -> selector` shape.

None of this shows up in the snapshots or the benchmarks, because both sample
through explicit `Greedy`/`Dist` pipelines rather than through
`sequence.sample(_:)` with a transform. The divergence is documented at the
code site and pinned by `RegressionTests`.

## The FFI layer

This is the biggest practical difference between the two ports, and it favors
Swift.

Rust needs `llama-sys`: a `bindgen` build script that parses `llama.h`,
generates thousands of lines of bindings into `OUT_DIR`, and hand-maintains a
CMake configuration to compile and statically link llama.cpp. It works well
and it is the standard approach, but it is machinery you own — `build.rs` is
~130 lines of CMake configuration and enum allowlists that must track upstream.

Swift's Clang importer does the same job at compile time from a two-line shim
header. `Sources/CLlama/include/CLlama.h` is literally `#include "llama.h"`,
and the module map points at that one header so the importer sees llama.cpp
and none of the other backend headers (cuda, sycl, vulkan) that also land in
the include directory. No generated code, no build script. The cost is that
the importer's mapping rules are its own, and the port hit three of them:

| What | Rust (bindgen) | Swift (Clang importer) |
|---|---|---|
| `struct llama_model` (incomplete C type) | `*mut llama_model` | `OpaquePointer`, no named type |
| `enum llama_vocab_type` | a Rust enum with `.rawValue` | imports as `UInt32`-backed; **collides with the C accessor function of the same name** |
| `llama_batch.seq_id` (`llama_seq_id **`) | raw pointer, manual arithmetic | `UnsafeMutablePointer<...>?` per level — three unwraps to write one row |

The enum/function name collision is worth calling out: `llama_vocab_type` is
both an enum type and a function in the C header, and Swift resolves the type
position to the function's return type. The port maps the enum in an explicit
`init(clangValue:)` switch rather than trusting the importer. These are all
discoverable in minutes, and bindgen has its own equivalents (it once required
a manual `rustified_non_exhaustive_enum` list for the same enums).

The link side is comparable. Both ports build llama.cpp as static libraries
via CMake. Rust does it in `build.rs`; the Swift package does it in a
40-line shell script (`scripts/build-llama.sh`) that mirrors the same flags
and merges the archives. The one genuinely awkward part on the Swift side is
that SwiftPM's `LinkerSetting` wants `-Xlinker` forwarding for
`-force_load`, and loading everything eagerly drags in llama-common's vendored
HTTP/TLS code (which wants OpenSSL) even though nothing references it. Lazy
static linking — the same thing Rust's build.rs does — resolves it.

## Traps worth knowing

Three real bugs came up in the port. Each one is a thing Rust would not let
you write, or would have caught, and each is now documented in the code at the
fix site.

**1. `String(cString:)` traps on invalid UTF-8.** Token pieces are raw bytes;
byte-fallback tokens decode to values like `0x80…0xFF` that are not valid
UTF-8 on their own. Rust's `String::from_utf8_lossy` never fails. Swift's
`String(cString:)` *traps* — not a thrown error, a hard crash with no
diagnostic. The fix is `String(decoding:as:)` with U+FFFD substitution,
centralized in one `lossyString(_:)` helper. This also cost an hour of
debugging a SIGBUS that pointed at a stack-guard error message instead of the
real cause.

**2. Overloads can recurse silently.** The natural design is one throwing
`piece(of:)` and one convenience `piece(of:) -> String?` built on it. Inside
the second, `try? piece(of: token)` resolves back to *itself* — not the
throwing overload — and the call recurses until the stack blows. There is no
compiler warning. The fix is distinct names (`piece(of:)` /
`pieceOrNil(of:)`), and the comment at the fix site says why.

**3. `String(format: "%s", ...)` is undefined with Swift strings.** Passing a
Swift `String` to `%s` segfaulted the benchmark harness. Swift has no format
checker for this. `String(format:)` with `%@` or plain interpolation is the
correct form.

None of these are Swift being bad; they are Swift being *permissive* where
Rust is strict, and the lesson is the usual one about unsafe-by-construction
string handling. But note how they cluster: they are all text and pointer
boundary problems, which is exactly where Rust's ownership and UTF-8-validated
`String` are load-bearing.

## Performance

Measured on the same machine, same model, same llama.cpp build
(`TinyStories-656K Q2_K`, Apple M4 Pro, macOS 27, CPU-only per the Rust test
fixtures' `n_gpu_layers = 0`). The Swift harness mirrors `benches/inference.rs`
bench for bench and reproduces criterion's `iter_batched(_, _, PerIteration)`
split — setup runs before every iteration and is excluded from the timing —
so each row measures the same work in both languages.

| Benchmark | Rust (criterion) | Swift (median) | Swift / Rust |
|---|---|---|---|
| `tokenize` | 6.76 µs | ~6.9 µs | 1.02× |
| `token_to_piece` | 0.027 µs | 0.073 µs | 2.7× |
| `decode_single_token` | 70.95 µs | 65–70 µs | ~0.95× |
| `generate_10_tokens` | 709.6 µs | ~635 µs | 0.90× |
| `context_creation` | 227.2 µs | ~212 µs | 0.93× |
| `sequence_extend_100_tokens` | 7.19 ms | ~6.9 ms | 0.96× |

Rust values are criterion's means (95% CIs are narrow, e.g. `generate_10_tokens`
707.1–712.1 µs). Swift values are medians across four separate runs; run-to-run
spread is a few percent, and `decode_single_token` is the noisiest row in both
harnesses (56–208 µs across Swift runs) because a single decode is barely
above the noise floor.

Two things to read out of this.

**The differences that matter are noise.** Every benchmark where real work
happens — model decode, tokenization of a sentence, context creation — lands
within a few percent, and Swift is if anything slightly faster on the
generation benches. That is the expected outcome and it says more about the
setup than the languages: 99% of the wall time in every one of these is inside
llama.cpp, compiled from the same C++ with the same flags on both sides. The
Rust and Swift wrappers are thin enough that their own overhead is rounding
error next to a matmul.

**The one real difference is tiny and explainable.** `token_to_piece` is
2.7× slower in Swift — and it is also 46 nanoseconds per call. This is the
wrapper's own work: both sides make one C call and build a `String`, and the
Rust path gets small-string optimization on a 14-byte piece while the Swift
path allocates a `UInt8` buffer and decodes through `String(decoding:as:)`.
At 73 ns versus 27 ns this is invisible in any real workload (you do this once
per generated token, against a 70 µs decode), but it is the one place where
the Swift wrapper's construction cost shows up.

**The actor overhead does not show up at all.** One thing the numbers do
*not* show is a penalty for the Rust actor's message round trips: Rust and
Swift are within noise on `generate_10_tokens`, so the actor's channel hop is
dwarfed by the decode. That is worth saying plainly, because it tempers the
design conclusion below: the Swift `Mutex` version is simpler, but the Rust
actor was never the performance problem.

## How each one feels

**Writing it.** Swift is faster to write for this kind of code. No lifetimes
on the sequence handle, no `Arc<Mutex<...>>` vocabulary, no `unsafe impl`
blocks, no macro that generates a protocol. The whole `Context` + `TokenSequence`
+ `Batch` layer is 285 lines of straightforward Swift against 460 lines of
Rust that include the actor machinery and its safety arguments (507 versus 494
once you count the comment lines — see the line-count table above). Conversely,
Rust makes you *state* the safety argument, which is exactly the documentation
a reader of this kind of code wants — the Swift port compensates by writing
those same arguments as doc comments by hand, and ends up with seven times as
many comment lines.

**Reading it.** The Swift is easier to skim: `guard let`, `throws`, and
labeled arguments (`push(contentsOf:)`, `transformInPlace`) mean the intent of
each call reads without looking anything up. The Rust is easier to audit for
correctness: the type system has already ruled out a class of bugs that the
Swift code merely has comments about. The `Token`/`Position`/`SequenceID`
distinction is a wash — Swift's structs make it real, Rust's `pub type` alias
is zero-cost and honest about being notation.

**Debugging it.** Swift's failure modes are worse where they exist: a `String`
trap or a silent overload recursion is a SIGBUS with a misleading crash report,
versus a Rust `Result` or a compile error. Rust's `cargo test -- --test-threads=1`
note (llama.cpp global state) is still there in both; the Swift suite runs in
parallel fine because the fixtures are a lazy singleton, which is a small
quality-of-life win over the Rust `OnceLock` plus test-thread constraint.

**Testing it.** Swift Testing (`@Test`, `#expect`, `#require`) is a genuinely
nicer test DSL than `#[test]` + `assert_eq!`: less boilerplate per test, better
failure output for free. The snapshot story is the opposite: `insta` is a
mature tool with `cargo insta review`, and the Swift port's snapshot support is
a 40-line hand-rolled JSON comparison with a `KOTOTAMA_UPDATE_SNAPSHOTS=1`
re-record flag. If snapshot testing were a bigger deal here, that gap would
matter.

**Portability.** This is the biggest asymmetry and it is not close. The Rust
crate builds on macOS, Linux, and Windows, with Vulkan and CUDA features
already wired up in `build.rs`. The Swift port is macOS-on-Apple-Silicon only
today. Swift runs on Linux and Windows, but the package as written leans on
Metal, `Synchronization`'s `Mutex` (macOS 15+/Swift 6), and Xcode tooling; it
would need real work to run elsewhere. If kototama is going to be a
cross-platform bindings project — which the repo's "polylot llama.cpp
bindings" mission suggests — Rust is the better center of gravity and Swift is
a good citizen on the platforms where it runs.

## When to reach for which

Swift if you are building a macOS/iOS app, a Swift service, or anything where
the audience is Swift developers and the goal is a safe, readable, idiomatic
layer over llama.cpp. The code is shorter, the API is more discoverable, the
FFI layer is smaller, and the performance is the same.

Rust if you need to ship to Linux or Windows, if you want the compiler to
enforce the safety arguments rather than document them, or if this crate is
going to sit under other-language bindings (the repo's Elixir and TypeScript
work) — Rust's ABI story and tooling for that are much better worn.

The single most transferable lesson from doing both: the Rust crate's actor
is a lot of machinery to buy what a `Mutex` provides when your public API is
synchronous anyway. The thing worth keeping from the Rust version is not the
actor but the *documentation of why* the shared state is safe to share. In
Swift that has to be a comment; in Rust it is code — and the line counts show
the swap almost exactly: 175 fewer lines of machinery, 188 more lines of
explanation. That trade is the whole comparison in one sentence.
