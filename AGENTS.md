# rusty-llama — developer notes

## Build

```sh
cargo build
```

## Tests

Tests live entirely in `tests/`. There are no inline `#[cfg(test)]` blocks in source files.

A test model is bundled at `./test-models/TinyStories-656K.Q2_K.gguf`. To use a different model, set `RUSTY_LLAMA_TEST_MODEL`.

### Run tests

```sh
cargo test -- --test-threads=1
```

`--test-threads=1` is required because the llama.cpp backend uses global state.

### Snapshot tests (insta)

Initial snapshots are created on first run with `INSTA_UPDATE=new`:

```sh
INSTA_UPDATE=new cargo test -- --test-threads=1
cargo insta review
```

After bumping llama.cpp, retake snapshots the same way and review the diff.

## Benchmarks

```sh
cargo bench
```

To use a different model, set `RUSTY_LLAMA_BENCH_MODEL`. Falls back to `RUSTY_LLAMA_TEST_MODEL`, then `./test-models/TinyStories-656K.Q2_K.gguf`.

HTML reports are written to `target/criterion/`.

## Coverage

Install `cargo-llvm-cov` once:

```sh
cargo install cargo-llvm-cov
```

Then:

```sh
cargo llvm-cov -- --test-threads=1
# HTML report:
cargo llvm-cov --html -- --test-threads=1
cargo llvm-cov --html -- --test-threads=1
# opens target/llvm-cov/html/index.html
```

## Model used for testing

The canonical test model is **TinyStories-656K Q2_K** (~540KB):

- HuggingFace: https://huggingface.co/mradermacher/TinyStories-656K-GGUF
- Bundled at `./test-models/TinyStories-656K.Q2_K.gguf`
- Override with `RUSTY_LLAMA_TEST_MODEL` if needed

## Bindings (hand-maintained)

The language bindings are **hand-written**, not generated. (An earlier attempt
used [alef](https://github.com/kreuzberg-dev/alef) to scaffold them, but it
could not handle `&mut self`, the `i32` token-type aliases, `Range` arguments,
generics, or the sampler surface, so the output had to be rewritten by hand.
We now own these directly.)

- `packages/elixir/` — Rustler NIF crate (`native/rusty_llama_nif`) and the
  Elixir wrapper modules under `lib/rusty_llama/`.
- `packages/node/` — NAPI-RS crate; `index.d.ts` TypeScript declarations are
  generated by `napi build`.

### Keeping bindings in sync with core

Each binding symbol mirrors a core method, named `<type>_<method>` (Elixir) or
the same snake_case fn name with a camelCase `js_name` (Node). When you add,
rename, or remove a public method on `Model`/`Context`/`Sequence`, update both
bindings to match.

`scripts/check-binding-coverage.ts` enforces this — it diffs the core API
against the bound symbols and fails CI on untracked drift. Methods that are
intentionally unbound (raw pointers, generics, the sampler API) live in
`scripts/binding-coverage.json` under `ignore`; tracked backlog items go under
`todo`. The checker runs in both Node and Deno. See `scripts/README.md`.
